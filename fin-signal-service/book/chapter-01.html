LESSON 01 / 04

讀懂測試的證據

從你已跑通的四項案例，建立 Python 自動化測試的判讀能力。

本課問題「測試通過」這四個字，究竟提供了什麼證據？

1.1 從 Android 的測試思維出發

當你測試一個 Repository，不一定要啟動 Activity、連線正式後端或操作真實資料庫。你會先決定測試邊界，再控制輸入並檢查結果。Python 完全沿用這套思維，pytest 只是你在這個生態系採用的執行器。

一個好測試通常有三段：Arrange 準備、Act 執行、Assert 驗證。對 PHP API 來說，這很像準備 request payload、呼叫 controller 或 HTTP 測試用戶端，再檢查 status 與 response body。

-m 的位置很重要：python3 -m pytest 的 -m 屬於 Python；pytest 自己也有一個 -m 選項，放在 pytest 後方時，用來依 marker 篩選測試。相同字母在不同工具裡不一定代表相同意思。

1.4 assert 是預期，不是輸入

左邊是程式算出的實際值，右邊是測試寫下的預期。它們不同時，pytest 會顯示 FAILED 並提供差異。你要調查的是程式錯了，還是測試預期錯了；不能只改 assert 讓結果變綠。

Python 的 assert 可被最佳化模式停用，所以不要把它當成正式 API 的必要輸入檢查。請求驗證應使用 Pydantic 或明確的例外處理；這與 Java assertions 不應承擔正式業務驗證的觀念相近。

LESSON 02 / 04

掌握 Python 專案的邊界

把執行環境、依賴、建置與工具設定分清楚。

本課問題同一台機器，為什麼「裝好了」卻可能 import 不到？

2.1 執行環境，先於程式本身

Android 工程師會先確認 JDK、Gradle wrapper 和 Android SDK；PHP 工程師會確認 CLI 與 FPM 使用的 PHP 版本是否一致。Python 同樣需要先知道「現在啟動的是哪個 interpreter」。套件安裝在某個環境，不代表其他環境也能找到它。

你提供的結果是 Python 3.13.16，執行檔為 /opt/homebrew/opt/python@3.13/bin/python3.13；pip 與 pytest 位於 Homebrew 的 site-packages。這次你用的是 Homebrew 環境，不是專案的虛擬環境。

site-packages 可以借用 Composer 的 vendor 來理解：都是第三方套件會出現的地方。但 Python 的套件位置通常由 interpreter 環境決定，不一定在專案目錄裡；Composer 的 vendor 則通常位於專案內。

2.2 虛擬環境隔離的是什麼？

venv 為專案建立獨立的套件安裝環境。它不是 Docker，不會隔離整個作業系統、網路或 MySQL。啟用環境主要是調整 shell 的尋找路徑，讓 python、pip 指向該環境。

不使用虛擬環境也能執行測試，但套件版本較容易互相影響。若系統提示 externally-managed-environment，使用虛擬環境即可。切換環境後，別假設之前安裝的 pytest 已存在，先用前面的診斷指令確認。

2.3 pyproject.toml：把設定分成三層

設定區責任你的舊經驗

[build-system]誰負責建置，建置時需要哪些工具。建置工具的選擇；不等於整份 Gradle 功能。
[tool.*]pytest、Ruff、setuptools 等工具的設定。類似各個工具的設定區，不是 Python 自動執行的程式。

FastAPI 處理 API，Uvicorn 啟動 ASGI 伺服器，Pydantic 負責資料驗證。dev 群組放測試與檢查工具。這是本專案的分類；例如 HTTPX 也可被正式服務用來呼叫其他 API，並非天生只能當開發工具。

>= 是版本下限，不是鎖定版本。可重現的部署還需要固定解析後的依賴版本或適當鎖檔流程。第一章先看懂環境與宣告，之後部署章再落實版本重現；工具不用同時學 pip、uv、Poetry 三套。

2.5 setuptools、pytest 與 Ruff 各司其職

setuptools 從 src 找套件。pytest 預設從 tests 找案例，並在測試期間把 src 加入模組搜尋路徑。asyncio_mode = "auto" 讓 pytest-asyncio 自動接手非同步測試及非同步 fixture；function loop scope 表示對應 fixture 的事件迴圈範圍為單一測試函式。

Ruff 的 E、F、I、UP、B、SIM 分別涵蓋風格、常見程式問題、import 排序、新版寫法、易錯模式與可簡化寫法。它們選擇「提醒哪些問題」，不會開啟或禁止某種 Python 語法。移除 select 會回到 Ruff 預設規則，並非完全停止檢查。

target-version = "py311" 是 Ruff 的相容性目標，不會替你安裝 Python 3.11；line-length = 88 是格式化等操作的行寬目標，也不會強制所有內容都恰好小於 88 字元。

進階：為什麼測試能 import，啟動服務卻失敗？

pytest 的 pythonpath 設定只影響測試程序。若套件未安裝，在一般 Python 程序裡不一定找得到 fin_signal。使用可編輯安裝，或在開發啟動 Uvicorn 時指定 --app-dir src，才能清楚處理模組搜尋路徑。這就像 Android Studio 能解析某個環境，不代表另一套 CLI 也自動擁有相同設定。

LESSON 03 / 04

把測試當成可執行規格

逐行讀懂模型、非同步、fixture 與資源生命週期。

本課問題測試不是逐行往下執行嗎？為什麼 fixture 會先跑？

3.1 先看這個專案的邊界

可以把 main.py 類比 PHP 的路由與 controller 邊界，service.py 類比業務服務，schemas.py 類比 DTO 與驗證規則。這是理解職責的借鏡，不是強迫套用 Android 的 ViewModel／Repository 層級；專案目前很小，不必為每層都新增抽象。

3.2 從實際的領域測試開始

@pytest.mark.asyncio 標記非同步測試；此專案的 auto 模式也能自動識別。async def 定義可被 await 的協程函式，test_ 前綴則讓 pytest 預設蒐集到它。三引號文字放在函式開頭叫 docstring，負責說明用途。

service = SignalAnalysisService() 建立類別實例，近似 Kotlin 的 val service = SignalAnalysisService()，這一步還沒有分析新聞。NewsAnalysisRequest(...) 建立並驗證輸入；使用 ticker="AAPL" 這種具名參數，能讓欄位與值清楚對應。

Python 寫法用既有經驗理解需要補上的差異
req: NewsAnalysisRequestKotlin 的型別宣告一般 Python 型別提示不自動執行驗證。
content=("第一段 " "第二段")多行拆開寫字串相鄰字串常值會串接；沒有逗號，不是 tuple。
result = await service.analyze(req)等待 suspend function 的結果不是自動開新執行緒；協作式等待需配合非阻塞操作。
0.0 <= result.confidence <= 1.0上下界判斷Python 支援鏈式比較，表示兩個範圍條件都成立。
SentimentType.BULLISHKotlin enum 的具名成員這裡是 StrEnum，也具有字串值。

3.3 Pydantic 不是只有一張型別標籤

ticker: str 是型別提示，Field(...) 中的省略號表示必填，長度限制則由 Pydantic 在建立模型時檢查。str_strip_whitespace=True 會先去掉字串前後空白，所以純空白 ticker 也會變成空字串而不合法。

PHP 後端工程師可以把它理解成 request validation 加資料物件。MySQL 的 NOT NULL、欄位長度或 CHECK 是另一層約束：API 驗證保護輸入邊界，資料庫約束保護持久化資料，兩者不能互相替代；本專案目前也還沒有寫入資料庫。

3.4 fixture 是按名稱注入的測試依賴

pytest 在執行測試前看見參數 async_client，就尋找同名 fixture。提供依賴的依據是參數名稱，不是後面的 : AsyncClient 型別提示。你可以借用 JUnit 的 before／after 理解前置與收尾，但 pytest fixture 還具有可組合、可依名稱注入與不同作用範圍的能力。

ASGITransport(app=app) 直接在程序內把 HTTP 請求交給應用，不會真的連到 http://test，也不需要先啟動 Uvicorn。base_url 主要提供組合相對網址所需的基底。

3.5 yield：把函式暫停在交接點

pytest 先執行 fixture，取出 yield 的值，把它交給測試參數。測試結束後，再恢復產生器、執行 yield 後面的程式。即使 assert 失敗，正常的 pytest 收尾流程仍會執行；如果程序被強制終止，就不能保證收尾。

在上面的例子裡，「清理資源」只是印字。你專案的真正清理來自恢復 fixture 後離開 async with，由 AsyncClient 的非同步 context manager 關閉資源。這很像 Kotlin 的 use 或 PHP 的 try/finally，但管理的是測試生命週期中的交接。

return 會結束這次函式執行，後面的程式不會再跑。含 yield 的同步函式則產生 generator；一般程式可透過 next() 推進，fixture 由 pytest 推進。含 yield 的 async def 是非同步產生器，不是同一種同步 generator。

進階邊界：ASGITransport 與應用生命週期

HTTPX 的 ASGITransport 不會自動觸發 FastAPI 的 lifespan。現有路由在 signal_service 為 None 時另有初始化邏輯，所以測試仍能成功。這不代表啟動生命週期已測到。未來若在 lifespan 建立資料庫連線，測試就需要另外管理啟動與關閉，不能只沿用這個 fixture 就假設連線已準備完成。

目前的 anyio_backend fixture 會回傳 asyncio，但這批測試使用 pytest-asyncio 的標記；該 fixture 沒有被它們直接要求，也不是這批測試使用 asyncio 的主要原因。

3.6 async 不等於自動平行

把 Kotlin 的 suspend 想法帶過來很有幫助：宣告可暫停，不代表工作真的切到背景執行緒。Python 事件迴圈在協程讓出控制權時，才能推進其他任務。阻塞式資料庫驅動或 time.sleep 放在 async def 裡，仍然可能阻塞事件迴圈。

現有服務用 async 介面保留之後接非同步 API 的空間。這不是「已經同時處理多筆新聞」的證據；未來呼叫模型或 MySQL 時，仍須選擇合適的客戶端與並行方式。

LESSON 04 / 04

用案例建立行為邊界

加入看跌案例與欄位驗證，用測試保護之後的修改。

本課問題怎麼新增一個真正有價值的測試，而不是把程式抄進 assert？

4.1 從可描述的行為開始

先寫下一句業務預期：「一則有明確負面訊號、沒有正面詞的新聞，應被判為看跌，並得到負分。」這是可驗證的行為，不需要測試去重寫服務的關鍵字迴圈。

現有服務會把標題與內文轉小寫，逐個檢查關鍵字是否為子字串。它計算的是命中的不同關鍵字數，不是同一個字出現幾次；事件分類先檢查財報，再檢查總經。理解這些目前行為，才知道測試資料是否夠明確。

4.4 422 測試：一次錯很多欄位有什麼限制？

現有 invalid_payload 同時讓 ticker、headline、content 不合法。它能證明這份 payload 被拒絕，卻不能獨立證明每個欄位的規則都正確。想隔離 ticker 的規則，其他欄位就必須保持有效。

@pytest.mark.parametrize 讓同一個測試跑三組輸入，所以它會被蒐集成三個案例。你可以把它理解成 JUnit 的參數化測試。最後的 assert 不只檢查 422，也確認錯誤位置包含 ticker，避免因其他欄位出錯而誤以為 ticker 驗證正常。

any(... for ... in ...) 表示只要其中一個錯誤項目符合就成立。預期 loc 使用 FastAPI 標準驗證錯誤格式；若未來自訂錯誤回應，就需要依 API 契約調整測試。

4.5 TDD：先紅、再綠、最後重構

新增看跌測試時，現有服務可能直接通過，這叫補測試，不代表完成了一次 TDD。TDD 是先提出尚未實作的新行為，讓測試因該行為缺失而失敗，再做最小修改使它通過，最後重構並保護既有行為。

01RED測試因預期的新行為缺失而失敗
02GREEN最小必要修改，讓行為符合預期
03REFACTOR改善結構，保持測試通過

例如先定義「unprofitable 不應只因內含 profit 而被判看漲」。先新增一則只包含這個陷阱詞的案例，觀察目前規則如何失敗，再考慮英文單字邊界匹配。修改前要想清楚：多字詞、標點、中文與不同語言的 token 邊界可能需要不同策略；正則表達式也不能解決所有語意問題。

4.6 非同步 API 的實戰入口

開發時可以啟動真正的伺服器，從瀏覽器或 curl 操作 API。這條路徑和程序內 ASGI 測試不同，開始涵蓋實際伺服器與網路連線。

Uvicorn 是 ASGI 伺服器，FastAPI 是 ASGI 應用框架，ASGI 是兩者溝通的介面規範。Android 可以借用 interface 契約來理解：呼叫方與實作方遵守同一份規則。但 ASGI 還規範非同步訊息與生命週期，不只是 Java／Kotlin 的一個型別宣告。

scope 包含連線資訊，receive 接收訊息，send 傳送回應。FastAPI 底層建立在 Starlette 之上，透過可呼叫物件的 __call__ 接收這三個參數。你平常只需寫路由函式，框架會處理交接，不必手動組出所有 ASGI 訊息。
